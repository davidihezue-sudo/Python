# Known limitations and what is not finished

Honest status of this build, so nobody is surprised later.

**Not verified against the real world**
* The existing site `eazyfoods.ca` could not be reached from the build environment, so its content, branding, catalogue and URLs were not imported. Product names, stores, chefs and prices in the demo data are invented. Placeholder SVG artwork stands in for photography.
* Stripe, SendGrid, Twilio, Firebase, Google Maps and Mapbox adapters are written but have never been run against the real services. See `INTEGRATIONS.md`.
* Tax rates are example values. Delivery zones, fee rules and commission rates are sensible defaults, not business decisions.
* The seeded history (orders, reviews, analytics events, payouts) is synthetic so dashboards have something to show. Numbers on a fresh production database start at zero.

**Product gaps**
* Customer order tracking draws an SVG route diagram from real coordinates. It does not render street map tiles, and there is no turn by turn navigation (drivers get an "Open directions" link to the phone's maps app).
* Masked phone calls are not implemented. Customers, stores and drivers talk through in app messages that never reveal phone numbers.
* Barcode scanning uses the browser `BarcodeDetector` API where available (Chrome on Android, some desktop browsers) and otherwise keyboard style scanners or typing the code. There is no bundled fallback decoder.
* Push notifications and offline mode: the driver app has a web manifest so it can be installed, but there is no service worker, so no push and no offline use.
* Only English is shipped. Text in the shopper pages goes through `t()` and `apps/web/src/i18n/en.json`, so adding French is a matter of adding `fr.json`, but the vendor, admin, marketing and driver portals still contain English strings written directly in components.
* Multi factor authentication and email verification are not enforced for staff.
* The customer checkout, cart and order screens are tested end to end in a browser. Portal screens were exercised with scripted sign in and page load checks, and key flows (vendor accepting and preparing an order) were driven through the real UI; not every button in every portal has an automated browser test.

**Engineering trade-offs**
* Payment provider calls happen inside a database transaction (simple and safe, but holds a connection during the call).
* Search is Postgres full text plus trigram similarity with a synonyms table. It is good to tens of thousands of products, not millions.
* Fraud detection produces signals for human review; there is no machine learning model.
* `apps/web/AGENTS.md` and `apps/web/CLAUDE.md` were generated by `next dev` (Next.js writes them automatically). `AGENTS.md` contains two em dashes, so `npm run lint:content` reports them. They are not part of the product; delete both files (and set `agentRules: false` in `apps/web/next.config.mjs`) to make the check pass.
* The Dockerfiles and `docker-compose.yml` were written but not built in the authoring environment (no Docker available), so treat them as a starting point.
